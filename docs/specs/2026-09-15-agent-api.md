# The agent API

*2026-09-15. Supersedes nothing — no earlier spec covers API keys, an external
surface, or write-back.*

## Why

Everything this agent writes dies inside the app or on a Google Calendar event.
Nothing else can ask "what does Acme owe this week, and in what words". The only
machine surface was `/api/v1/*`, which authenticates a Firebase ID token and can
write anything, so handing it to a third party was never an option.

`/api/agent/v1/*` is a second rail: an API key, one client, a narrow read
surface, and a way to report back what actually went out.

## The shape

```
GET  /api/agent/v1/clients                             what this key can see
GET  /api/agent/v1/schedule                            the pieces, with copy
GET  /api/agent/v1/schedule/{slotId}                   one piece, re-read
GET  /api/agent/v1/brand                               voice, positioning, visual
GET  /api/agent/v1/logo                                302 to the logo
POST /api/agent/v1/schedule/{slotId}/published         it went out
POST /api/agent/v1/schedule/{slotId}/failed            it did not
```

`Authorization: Bearer mk_live_…`. Errors are `{ error, code }` — a divergence
from the house `{ error }`, because an external caller has to branch on
something stable and prose is not that. Codes: `invalid_key` (401),
`scope_missing` (403), `not_found` (404), `invalid_body` (400), `already_published`
(409), `invalid_range` (422), `not_configured` (503).

There is **no client id in any path**. A client-scoped key names its client, so
tenancy is decided at the key rather than on every route. Since
`2026-09-16-mcp.md` a key may instead cover a whole agency, in which case every
route takes `?client_id=` and `targetClientId` decides — see that spec.

## Decisions worth the ink

**A separate namespace, sharing no helper with the session rail.** Serving two
auth rails through one helper is how a handler ends up with privileges it never
asked for. `lib/marketing/agent/route-helpers.ts` imports nothing from
`lib/marketing/route-helpers.ts`, and there is no `Session` anywhere in the key
path to inherit.

**The sha256 of the key is the Firestore document id.** Verification is one
`get()` — no query, no index, no enumeration. It also means the secret is never
compared in our process at all: Firestore's key lookup does the matching, so
there is no string equality over key material and no timing signal to leak.
Unsalted sha256 is safe here *only* because the preimage is 32 bytes of
`randomBytes`; a shorter key would need a different design.

**No new environment variable.** A pepper would buy nothing against a 256-bit
preimage while adding a value that, rotated or missing on one deploy, silently
invalidates every key in existence. `.env.example` is the deploy checklist and
every entry on it is a liability.

**The publish gate is `confirmed` AND copy that matches its brief.** Status
alone is not enough: somebody confirms a piece, somebody then fixes a typo in
the hook, and the copy is now written from a brief that no longer exists — while
the status still says confirmed, because nothing demotes it. `ready_only`
therefore **defaults to true**; seeing anything less finished must be asked for.

**`updateSlot` is not reused for write-back.** It records a learning signal on a
human edit (a robot's publish report is not feedback about the brief), it stamps
`lastHumanEditAt` (which is how calendar reconciliation tells a hand edit from
agent output), and reusing it would mean widening `SlotPatch` — which the
browser's own PATCH route accepts, so anyone with a session could forge a
publication. `markSlotPublished` and `markSlotFailed` are siblings instead.

**`markSlotPublished` runs in a transaction.** Read-decide-write is otherwise a
check-then-act race: two reports arriving together would both see no
publication, both write, and the 409 that protects the client would never fire.

**A failed publish does not move the status.** `cancelled` and `skipped` free
the slot's quota, so demoting a failure would have the next plan run propose a
replacement for a piece still sitting there waiting to be retried.

**The projection is not `serializeSlot`.** That function carries `plan_run_id`,
`gap_id`, `needs_theme` and six `google_*` fields — internal state that means
nothing to a publisher and that we would then be committed to keeping stable.
`projectSlot` is a narrow, pinned list, and `project.test.ts` asserts the exact
key set so a rename cannot happen by accident. It also strips `CopyBlock.note`,
which is production direction and must never be published.

## Rate limiting: deliberately absent

An in-memory limiter is worse than none on serverless — per-instance, reset on
every cold start, and it *looks* like protection. A Firestore counter costs a
write per request and funnels every request for one key onto one document.

What ships instead, all free: a 92-day cap on any range, `limit` clamped to 200,
a format check before any Firestore read, `updated_since` so a poller re-reads
nothing, and instant revocation. `lastUsedAt` is throttled to once an hour for
the same reason — a read endpoint must not cost a write.

## Known holes

- **A confirmed piece is not demoted when its brief is edited.** The API refuses
  to serve it and both schedule screens warn, but the status still reads
  "released". Fixing it properly needs `diffBrief` in the write path, because
  the editor sends all six brief fields on every save and a no-op would
  otherwise un-release a piece.
- **`updated_since` is at-least-once, not exactly-once.** Calendar sync
  re-stamps `updatedAt` on every slot it touches whether or not anything
  changed. A poller must dedupe on `id`.
- ~~**One key per client.**~~ Resolved in `2026-09-16-mcp.md`: a key may now be
  agency-scoped, because configuring one connector per client by hand does not
  scale past about three.
- **No media.** The copy names slides and shots, but no images or video exist
  anywhere in the system. An Instagram agent cannot publish a carousel from
  words alone. Either the agent makes its own assets, or that is the next
  storage project after the logo.
- **No audit log.** Which key read what, and when, is not recorded beyond
  `lastUsedAt`.
- **No file storage.** `GET /logo` redirects to the hand-typed `logo_url`,
  validated to http/https so it is not an open redirect. When storage lands,
  the endpoint does not change — only what the URL points at.
