# MCP: the same API, spoken to an assistant

*2026-09-16. Builds on `2026-09-15-agent-api.md`, which it does not replace.*

## Why

`/api/agent/v1` is the right shape for a headless publisher — a cron job with a
queue and a stable message id. It is the wrong shape for the consumer we
actually have, which is a language model in Claude Desktop or Claude Code. Over
REST somebody writes integration code and keeps a spec in sync. Over MCP the
model reads the tool descriptions, and the rules that matter travel with the
tools instead of living in a document that is not in the context window.

**This is a second face, not a rewrite.** Every judgement already existed and
was already tested: `targetClientId`, `resolveRange`, `projectSlot`,
`copyState`, `publishable`, `publishDecision`, `markSlotPublished`. The MCP
layer translates; it decides nothing.

## The endpoint

`POST /api/mcp`. Stateless Streamable HTTP. `GET` and `DELETE` answer 405 —
there is no stream to resume and no session to delete.

Stateless because this runs on serverless functions with no memory shared
between invocations: a session id would name state that is gone by the time the
next request arrives. A new `McpServer` and a new transport are built per
request and closed in a `finally`. Neither is ever hoisted to module scope —
the transport tracks whether it has already handled a request, and the key
differs per caller, so a shared one would serve the second caller with the
first one's permissions.

## Tools

| Tool | Scope |
|---|---|
| `list_clients` | `brand:read` |
| `list_scheduled_content` | `schedule:read` |
| `get_content` | `schedule:read` |
| `get_brand` | `brand:read` |
| `report_published` | `schedule:publish` |
| `report_failed` | `schedule:publish` |

The list is filtered by the key's scopes at registration. A read-only key does
not merely get refused when it calls `report_published` — it never sees the
tool. A model shown a tool it cannot use will call it, be refused, and try
again; and the list is itself a disclosure of what the system can do.

## Decisions worth the ink

**The official SDK, not a hand-rolled dispatcher.** It ships
`WebStandardStreamableHTTPServerTransport`, whose `handleRequest(req: Request):
Promise<Response>` is exactly the App Router route-handler contract. The
Node-oriented class is a thin wrapper around it. Reimplementing protocol version
negotiation to avoid a dependency already on disk would be reinventing a moving
protocol. The route bundle came out at 108K — the Express and stdio paths the
SDK also carries tree-shook away, which was the risk worth checking first.

**Both dependencies are now declared and pinned.**
`@modelcontextprotocol/sdk@1.29.0` and `zod@4.3.6` were previously present only
transitively — the SDK arrived through `shadcn`, and would have vanished with
it. `zod` is a required peer dependency and `registerTool` accepts only Zod
schemas, never raw JSON Schema. It is confined to tool input schemas; the
`parse*` convention is untouched everywhere else.

**Annotations are set in full on every tool.** The SDK's defaults are the unsafe
ones — `destructiveHint` and `openWorldHint` both default to *true* when
omitted — so a read tool that simply forgot to mention it is presented to the
host as destructive, and operators learn to click through warnings. A test
asserts all four are present on every tool.

**A derived idempotency key.** Over REST the caller is a queue with a stable
message id. Over MCP it is a model that may publish, lose the thread, and
report again with a *different* key — at which point `publishDecision`
correctly but uselessly answers `already_published` for a post that went out
exactly once, and nothing the model can do will record it. So when no key is
supplied, one is derived from `sha256(slotId + " " + externalId)`: an identical
retry reproduces it and replays, while a genuine second publish has a different
platform id and still conflicts.

**Prose, not JSON.** Each read tool returns readable text. A wall of JSON makes
the model do parsing it is mediocre at and spends context on punctuation.
Rendering happens from the *projection* rather than the slot, which is the
second line of defence on the rule that would be most embarrassing to break:
`projectSlot` has already stripped `note` — production direction like "shot 2,
cut to the whiteboard" — so the renderer cannot emit one even by mistake.

**Unready pieces are hidden by default**, as over REST. A model shown a draft
alongside a released piece has no reliable way to keep them apart across a long
conversation.

## The agency key

Per-client keys are fine for a script holding twenty secrets silently. They are
not fine when a *person* configures twenty connectors by hand. So a key is now
either client-scoped (`clientId` set) or agency-scoped (`clientId: null`, sees
every active client in the agency).

`targetClientId` is the pure function that decides which client a request is
about, and it is where the whole multi-tenant story now lives:

- **client key** — an absent or matching id resolves to the key's own client. A
  *different* id reads as `not_found`, never 403: a 403 would confirm the id
  exists and turn the parameter into an oracle for enumerating other agencies.
- **agency key** — an id is required. It refuses to guess, because defaulting to
  "the first client" would act on the wrong one and report success, which is the
  worst possible shape for a bug in a tool a model calls.

Resolving an id is not authorisation. The `client.agencyId === key.agencyId`
check that follows is, and it runs for both kinds.

REST followed suit so the faces cannot drift: every `/api/agent/v1/*` route
takes an optional `?client_id=`, and `GET /api/agent/v1/client` became
`GET /api/agent/v1/clients`.

Agency keys are minted at `/settings` — the app's first agency-level screen, and
the thing the login page has promised all along. Per-client keys stay on the
client's own API access page; the two have very different blast radius, and
where you find a key should tell you which kind you are holding.

## Connecting

```bash
claude mcp add --transport http numerico-marketing \
  https://marketing.numericosoftware.com/api/mcp \
  --header "Authorization: Bearer mk_live_…"
```

```jsonc
// Claude Desktop — claude_desktop_config.json
{
  "mcpServers": {
    "numerico-marketing": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://marketing.numericosoftware.com/api/mcp",
               "--header", "Authorization: Bearer mk_live_…"]
    }
  }
}
```

## Known holes

- **No OAuth 2.1.** Auth is a static bearer key, which both clients above can
  send. A *native* Claude Desktop custom connector — added by URL with no
  `mcp-remote` bridge — expects the OAuth flow with dynamic client
  registration. That is its own project.
- **No resources or prompts.** The SDK supports both; tools alone are
  universally supported by clients. The brand document is a better fit for a
  resource and can move later.
- **Nothing stops a model reporting a publish that never happened.** The tool
  description says so plainly and the host can prompt, but the system has no way
  to verify a post exists on a platform it cannot see. The idempotency key
  limits the damage to one false record, not a loop of them.
- Rate limiting, audit logging, media and file storage — unchanged from the REST
  spec's known holes.
